# Candidates and committing

Open **Candidates** (`/candidates`) to review proposed work separately from the committed queue. Before committing, decide whether the work is needed, where it belongs, and what would count as finished.

1. Read the proposal and fill or edit **Acceptance**. Write observable conditions a reviewer can check.
2. If it needs a parent, choose a legal location; work other than a project needs a parent to be committed. Fill the other required fields. For a bug candidate, set a priority; that priority determines its SLA.
3. Click **Commit**. The proposal leaves Candidates and follows its target workflow state in the committed queue. Commit means the team takes it on; it does not mean delivery has been accepted.

To decline a proposal, choose a **Resolution**, add a **Reject reason** when required, and click **Reject**. To defer the decision, use **Snooze 7d** or **Snooze 30d**; **Wake now** brings a snoozed item back.

For multiple proposals, select their cards and use **Batch Commit** or **Batch Reject**. Check each item's acceptance and placement first; the bulk action does not invent missing contract details. Read the result before assuming all selected items went through.

Some narrowly defined bugs, incidents, or proposals covered by an enabled [autonomy policy](../autonomy-policy.md) may enter committed work without a manual Candidates decision. See [bugs and incidents](bugs-and-incidents.md) and [working with agents](agents.md).
